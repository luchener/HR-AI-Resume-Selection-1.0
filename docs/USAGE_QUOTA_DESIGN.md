# 每日使用次数配额 — 功能设计定稿

> 版本：v1.0（设计定稿，未动代码）
> 范围：每账号每日「简历分析」次数配额，管理员可逐账号/全局配置，次数用完有明确提示（可联动邮件通知）
> 与现有功能的关系：复用现有「使用统计埋点」（`record_user_usage(user_id, "analysis")`）做**校验**，不新增扣减机制；复用现有公告/邮件通知基建与前端提示组件。

---

## 1. 需求目标

1. **按账号限次**：管理员可对单个账号设置每天可使用分析次数；未单独设置的账号使用全局默认值。
2. **每日重置**：配额按自然日（服务器本地时区）重置，无需定时任务（按日期键天然过期）。
3. **用完即止**：次数用完后分析不可发起，返回明确提示；前端同步禁用入口。
4. **用完通知**：用户端即时提示（拦截文案 + 面板状态）；可选每日一封邮件提醒（管理员开关，防轰炸）。
5. **管理员不受限**（默认）：`is_admin` 账号跳过配额校验，保证管理端可随时验证功能。

---

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 配额（daily_limit） | 某账号每天允许的**成功分析次数**上限。`-1`/未配置 = 不限；`0` = 禁用分析；`≥1` = 具体次数。 |
| 已用次数（used） | 当日该账号**成功完成的**分析次数（直接读现有 `data/usage/<user_id>.json` 当天 `analysis` 计数）。 |
| 全局默认 | 对所有未单独配置账号统一生效的每日限额（配置项，默认**不限**，即默认不改变现状）。 |
| 自然日 | 服务器本地时区 `YYYY-MM-DD`（与现有 usage 统计键一致），0 点自动进入新一天。 |

**为什么用"校验 + 现有埋点"而不是"新扣减"：**

- 现有 `_run_hr_analysis` 成功后才 `record_user_usage(user_id, "analysis")` 且原子落盘，天然满足"失败不计数"。
- 校验 = 分析开始前读当天 `analysis` 计数与限额比较；扣减动作 = 既有埋点，无需重复实现、无双写风险。
- 单份/批量/SSE 流式共用同一埋点路径，配额口径与"使用统计"完全一致（管理端现有排行/明细可直接复用）。

## 3. 数据存储

新增一个 JSON 文件（零数据库，原子写，风格与现有存储一致）：

```
data/quota/limits.json
{
  "quota_enabled": false,           // 全局配额总开关（关=全部账号不限次，回到现状）
  "default_daily": 10,              // 全局默认每日限额；-1 或缺省 = 不限
  "users": {                        // 逐账号覆盖；仅存被单独配置过的账号
    "zhangsan": {"daily_limit": 3, "email_notify": true, "analysis_enabled": true, "updated_at": "..."},
    "lisi":     {"daily_limit": 0, "email_notify": false, "analysis_enabled": true, "updated_at": "..."},
    "test01":   {"analysis_enabled": false, "updated_at": "..."}   // 仅禁用分析，不设限额
  },
  "email_notify_enabled": false,    // 全局邮件提醒总开关
  "updated_at": "..."
}
```

要点：

- 逐账号配置缺失时回退 `default_daily`；`default_daily` 缺失或 `-1` = 不限。
- 独立于 `data/users/`（不侵入用户记录结构，不改 `create_user`/`update_user`）。
- `config.py` 新增 `QUOTA_LIMITS_PATH = os.path.join(DATA_DIR, "quota", "limits.json")`，启动时 `mkdirs`。
- 邮件提醒的去重标记不落盘配额文件：按 `email_notify_date:username` 记入 `data/rate_limits/`（复用 `_rate_limited` 的键空间，窗口 1 天），保证**每账号每天最多一封**。
- **无邮箱降级**：账号未绑定邮箱（如测试号 admin）时，邮件提醒自动跳过、不报错 —— 用户端**弹窗提示不受影响**（弹窗是本分逻辑，不依赖邮箱）；管理端列表中该账号邮件列显示「未绑定邮箱」灰徽章，开关不可用。

## 4. 计次与校验规则

### 4.1 校验入口（唯一）

`hr_analysis()`（`POST /api/v1/resumes/hr-analysis`）在**校验参数之后、调用 AI 之前**执行 `_check_quota(user_id, requested_count)`：

```
def _check_quota(user_id, requested_count):
    user = auth_mod.find_user_by_id(user_id)
    # ① 账号级分析开关：关闭 = 该账号整体禁用分析（独立于配额开关，管理员同样生效）
    if per_user_cfg(username).get("analysis_enabled", True) is False:
        拒绝 → 403「该账号的分析功能已被禁用，请联系管理员。」
    # ② 全局限额开关：关闭 = 配额全不生效（回到现状；不影响 ①）
    if not quota_global().get("quota_enabled"):
        return 不限
    # ③④ 生效限额（管理员未显式配置则不限；显式配置后同样受约束）
    limit = _effective_limit(username, user)  # 管理员未配置 > 逐账号 > 全局默认 > 不限
    if limit is None or limit < 0:
        return 不限
    used = today_analysis_count(user_id)      # 读 usage 当天 analysis
    remaining = limit - used
    if remaining <= 0:
        _notify_quota_exhausted(username, limit, used)   # 邮件（可关/无邮箱跳过）
        拒绝 → 429「今日分析次数已用完（限额 N 次），明天 0 点重置。」
    if requested_count > remaining:
        拒绝 → 429「本次需要 N 次，今日剩余 M 次，请减少选择或明天再试。」
    放行
```

**开关优先级（自上而下）**：**账号分析开关 → 全局限额开关 → 生效限额**。即：禁用态**独立于配额总开关**（`quota_enabled=false` 时禁用仍然生效），且禁用对管理员同样生效；`quota_enabled=false` 时所有**限额**配置（含账号级）一律不生效。管理员在**未显式配置 `daily_limit`** 时豁免额度（全局默认不适用于管理员），一旦显式配置具体次数，管理员同样受该限额约束（便于管理员自助验证限额逻辑）。

> `quota/me` 必须与本节口径**完全一致**（否则前端拿不到禁用态、不会弹窗提示，用户表现为"分析失败但没有原因"）。

- `requested_count`：单份 = 1；批量 `resume_ids` 长度 = N（与埋点口径一致：批量 N 份成功记 N 次）。
- `?stream=true` 流式：同样在**首帧前**校验一次，流式期间不重复校验。
- **并发边界**：校验通过后分析执行的窗口内，另一请求可能把剩余次数耗尽 → 实际可能超出 1 份。属可接受软边界（读-校验-埋点三段非原子）；如需硬性，可在校验处加 `_QuotaLock` 文件锁并在锁内校验+预占（预占会导致"发起未完成也占次数"，与"成功才计次"语义冲突，故不采用）。设计取**软限制 + 文案兜底**。

### 4.2 计次

- 沿用现有埋点：分析成功后 `record_user_usage(user_id, "analysis")`，**不改动**埋点逻辑。
- 失败（AI 报错/解析失败）不计数 → 用户重试不扣次数。
- 已归档/历史分析不计入当日配额（配额只度量今日新发起的成功分析）。
- `improve_resume`（AI 润色）、`review_markers` 等**不在本期配额范围**（如需扩展，只改校验入口，埋点已存在）。

### 4.3 重置与变更时效

- 重置：`usage` 按天键自然重置，0 点即新配额；限额配置随时修改**立即生效**（下一次校验读到新值；已用完的账号改大后即刻可用）。

## 5. 通知与提示

### 5.1 用户端（前端即时提示）

| 场景 | 呈现 |
|---|---|
| 剩余次数充足 | 分析面板常驻状态条「今日已用 X / 上限 Y 次」（未配置限额则不显示） |
| 剩余 ≤ 2 | 状态条变橙 + 文案「今日仅剩 N 次」 |
| 已用完（剩余 0） | 状态条变红 +「今日次数已用完，明天 0 点重置」；点击分析按钮弹「次数已用完」弹窗 |
| 发起分析被 429 拒绝 | 顶部 notice banner（err）+ **弹窗**（见 5.3）；批量不足时给出「需 N 剩 M」明细 |
| 进入页面时已用完 | 仅弹一次弹窗（会话内去重，见 5.3），不重复骚扰 |
| 账号分析功能被禁用 | 面板顶部红色提示条「当前账号的分析功能已被管理员禁用，无法发起分析。」+「查看原因」按钮；点击分析按钮/进入页面各弹一次「分析功能已被禁用」弹窗（含处理方式） |

### 5.2 邮件提醒（可选，管理员开关）

- 全局开关 `email_notify_enabled` + 逐账号 `email_notify`，二者同时开启才发。
- 触发点：`_check_quota` 判「已用完」时检查去重键 `quota_email:<username>:<today>`，未发过则通过现有 SMTP 发送一封简版邮件（标题「分析次数已用完」，正文 = 已用/限额/重置时间；复用 `mailer.send_broadcast_email` 单收件人能力或 `render_broadcast_plain` 简版）。
- 去重：每账号每天最多一封（`data/rate_limits/` 窗口 1 天键），不发轰炸邮件。
- **无邮箱账号跳过**：用户记录无 `email` 时直接跳过发送（不报错、不入审计失败日志）；管理端展示「未绑定邮箱」。
- 日志：审计 `quota_email_sent`。

### 5.3 次数用完弹窗（用户端核心提示）

- 新建轻量组件 `quota-modal.tsx`（复用公告弹窗的视觉语言：遮罩 + 卡片 + 200ms/140ms 动画 + Esc/✕/按钮关闭 + prefers-reduced-motion；**点遮罩不关闭**防止误关）。
- **触发时机（3 种，均按"本次会话只弹一次"去重，key = 触发类型 + 当日日期）**：
  1. 发起分析被 429 拒绝 → 立即弹「今日次数已用完」（含后端明细文案）；
  2. 页面加载时 `quota/me` 返回 `remaining=0` → 进入页面后弹一次（不打断首次渲染，延时 300ms 淡入）；
  3. 分析成功且剩余降为 0 → 弹「这是今日最后一次分析，明天 0 点重置」。
- **弹窗内容**：
  - 标题：⚠ 今日分析次数已用完 / 已用完最后次数
  - 正文：今日限额 N 次、已用 N 次、明天 0 点自动重置；批量场景附明细「本次需 N 次，剩余 M 次」。
  - 按钮：「我知道了」关闭；「联系管理员」→ 跳转邮箱/联系页（如配置）。
- **账号被禁用（非次数不足）**：403 返回时弹**专用弹窗**（variant=`disabled`，标题「分析功能已被禁用」+ 原因「该限制与配额开关无关，需管理员开启」），同时保留顶部 notice（err）与面板状态条红色提示。禁用态**不显示重置时间**（不同于次数用完）。分析按钮保持**可点击**——点击即弹窗说明原因，避免"点击无任何反馈"。
- **不弹窗的场景**：剩余 ≤2 只在面板状态条变橙提示，不弹窗（避免打扰）；邮件提醒是弹窗之外的附加通道。

## 6. 后端接口

### 6.1 新增（管理员）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/quota/settings` | 返回 global（默认/总开关）+ 逐账号列表（含 username、daily_limit、今日 used、remaining、email_notify、来源=继承/自定义） |
| PUT | `/api/v1/admin/quota/settings` | 设置全局 `{quota_enabled, default_daily, email_notify_enabled}`；审计 `quota_setting_update` |
| PUT | `/api/v1/admin/quota/users/<username>` | 设置单账号 `{daily_limit, analysis_enabled, email_notify}`；审计 `quota_user_update` |
| DELETE | `/api/v1/admin/quota/users/<username>` | 恢复为全局默认（移除自定义配置）；审计 `quota_user_reset` |

- 入参校验：`daily_limit` 整数 `[-1, 1000]`，或 `null`/`""`/`"abc"` 中的前两者（`email_notify` 布尔；`"abc"` 或越界 → 422）。
  - `null` / `""` = **未配置**（逐账号 = 继承全局默认；全局默认 = 不限）
  - `-1` = **显式不限**（覆盖全局默认，这是与"未配置"的关键区别 —— 早期实现把 `-1` 折叠成 `null`，导致"设为不限"实际回退全局限额）
  - `0` = 禁用分析（次数归零）
  - `1~1000` = 每日具体次数
- 目标账号校验：不存在 → 404；目标为管理员时允许配置：**不填写 `daily_limit` 默认不限，填写具体次数后管理员同样受该限额约束**（前端编辑弹窗对有管理员的账号给出说明）。
- 管理端返回的每行同时给出 `daily_limit`（**生效值**，含继承）与 `raw_daily_limit`（**显式配置值**，`null` = 未配置）——编辑弹窗回显必须用 `raw_daily_limit`，否则"继承默认"会被误存成"自定义同值"。
- 返回统一 `{"request_id": rid, "data": {...}}`；所有写操作走 `record_admin_op` 留痕。

### 6.2 新增（用户端）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/quota/me` | 返回 `{configured: bool, unlimited: bool, daily_limit, used, remaining, resets_at: "YYYY-MM-DD 00:00"}`；管理员返回 `{unlimited: true}` |

### 6.3 变更（既有路由）

- `hr_analysis()`：插入 `_check_quota`（见 4.1）。其余不变。

## 8. 权限与安全

- `/api/v1/admin/quota/*`：管理员（现有 `admin required` 装饰器体系）。
- `/api/v1/quota/me`：登录用户，仅返回本人数据（按 `_current_user_id()` 取）。
- 配额校验在**鉴权之后**、AI 调用之前，防止绕过（不依赖前端禁用）。
- 金额/次数无泄漏风险：批量不足时只回显「需 N 剩 M」。
- 邮件提醒走既有 SMTP + 审计；去重键防轰炸。
- 用户名参数沿用现有 `<username>` 路由校验（仅 `[a-zA-Z0-9_-]`）。

## 9. 测试计划（unittest，沿用现有风格）

| 用例 | 断言 |
|---|---|
| 未配置配额（默认不限） | 放行，行为与现状一致 |
| 配置全局默认 3 | 第 4 次（无论单/批）返回 429 + 文案 |
| 批量不足 | 需 3 剩 2 → 429，提示明细 |
| 失败不计数 | AI 报错后重试不计入 used |
| 全局开关 quota_enabled=false | 所有限额配置不生效（含账号级），回到不限 |
| 账号开关 analysis_enabled=false | 该账号 403「分析功能已被禁用」；管理员同样生效 |
| 开关优先级 | 禁用 > 管理员豁免 > 限额；禁用时不走次数用完逻辑 |
| 管理员跳过 | is_admin 即使 used≥limit 也放行（前提：未被禁用、全局开关开） |
| 逐账号覆盖全局 | lisi 3 vs 默认 10 |
| 0=禁用 / -1=不限 | 边界值 |
| 重置 | 模拟次日日期键 → used 归零（读 usage 键） |
| 邮件提醒 | 开关+去重：当天仅 1 封；`quota_email_sent` 审计 |
| 设置接口 | PUT 校验 daily_limit 范围；DELETE 恢复默认；审计 op 记录 |
| 用户端 me | configured/unlimited/remaining/resets_at 正确；管理员 unlimited=true |
| 弹窗会话去重 | 同一会话内 429/加载/成功耗尽三类弹窗各只弹一次（按日期键） |
| 无邮箱账号 | email 为空时邮件提醒跳过、不报错；管理端列表显示「未绑定邮箱」 |
| 并发软边界 | 文档化（不做硬断言） |

## 10. 边界与本期不做

- **不做**：套餐/次数包/充值、跨账号转移、管理员也限次（默认豁免）、`improve`/`review_markers` 计次、配额导出。
- **软限制**：并发窗口可能超 1 份，接受（低成本、语义一致优先）。
- 默认行为不变：不配置任何配额时系统与现状完全一致（零影响上线）。

# 登录防爆破与账号冻结设计（v2 — 受限登录 + 邮箱自助解冻）

> 配套文档：`docs/INVITE_CODE_DESIGN.md`（邀请码注册机制 v3）。两者同属本轮账号安全加固，可一并实施。
> v2 核心变更：解决 v1"仅管理员解冻"可被恶意利用冻结他人账号的 DoS 问题 —— 冻结后走**受限登录 + 邮箱自助解冻**，管理员解冻保留为兜底。
> 本文档只做设计。评审通过后按 §9 落地清单实施。

## 0. 一句话结论

登录接口（`POST /api/v1/auth/login`）目前对密码错误无任何次数限制。补丁采用三级阶梯：

1. **L1 冷却**：同一账号连续失败 ≥3 → 冷却 5 分钟（冷却期再试直接拒绝，密码正确也拒）。
2. **L2 冻结**：10 分钟窗口累计失败 ≥6 → 账号冻结（拒绝一切密码登录）。
3. **解冻**：被冻结账号可在登录页输入**正确密码 + 邮箱验证码自助解冻**（本人证明），或走管理员后台/CLI 兜底解冻。

> 核心思路：**冻结的不是"这个账号"，而是"这个账号的所有密码尝试"** —— 账号本人有邮箱这把钥匙，攻击者没有。恶意冻结他人账号失去意义（受害者 1 分钟自助解冻，攻击者反而暴露邮箱）。仅管理员解冻保留为兜底通道（如账号未绑定邮箱的极少数老账号）。

---

## 1. 现状与风险

- `app.py` 的 `login()` 直接调 `auth_mod.authenticate_user`，无限流、无失败记录。
- 风险：在线对某账号密码字典爆破；对全网用户名批量撞库。
- 现有防护仅两点：PBKDF2-SHA256 慢哈希（减慢）、统一错误文案（防枚举）。慢哈希只是"减慢"，没有"停止"——仍需显式限流。

## 2. 锁定策略（v2 精确语义）

### 2.1 三级阶梯

| 阶段 | 触发 | 行为 | 响应 |
|---|---|---|---|
| L0 正常 | 无冻结，连续失败 <3，窗口失败 <6 | 正常校验 | 错误 → 401 统一文案 |
| L1 冷却 | 连续失败 ≥3 且距上次失败 <5 分钟 | 拒绝校验（含正确密码） | 429 + `Retry-After`，文案"X 分钟后重试" |
| L2 冻结 | 10 分钟滑动窗口累计失败 ≥6 | 拒绝一切密码登录 | 423，文案"账号已冻结，可用正确密码+邮箱验证码自助解冻，或联系管理员" |

### 2.2 判定细节

- **失败口径**：一切未通过登录校验的尝试，含 401（密码错）与 L1 冷却中被 429 拦下的尝试（不等待冷却反复试探也计入窗口，加速冻结）。L2 后不再计数。
- **窗口**：滑动 10 分钟，过期条目惰性清理。
- **连续失败**：登录成功后清零；冷却期满后的下一次失败续接。
- **冻结判定时机**：每次失败落账后检查窗口计数，≥6 → 冻结。
- **冻结后密码校验仍执行一次（防时序差异泄露）**：校验通过 → 走自助解冻分支；失败 → 423。见 §3.2 安全性论证。

### 2.3 防跨用户名批量爆破（每 IP 上限）

账号级策略覆盖不了"对大量不存在用户名撞库"，补一条独立于账号的每 IP 失败上限：每 IP 在 10 分钟窗口内失败 ≥10 → 429 冷却 10 分钟（登录与注册接口统一计入）。

## 3. 自助解冻（v2 核心）

### 3.1 解冻流程

```
登录页: 用户名 + 密码 + 邮箱(须手动填写与绑定邮箱一致) + [发送邮箱验证码] + 验证码
发码: POST /api/v1/auth/unfreeze/send-code {username,email}
      1. 账号不存在 → 404；未冻结 → 409；邮箱≠绑定邮箱/未绑定 → 422（提示联系管理员）
      2. 生成并发送解冻验证码（60s 冷却）
解冻: POST /api/v1/auth/unfreeze {username, password, email, code}
      1. 校验该账号 frozen=true（否则 409「该账号未被冻结」）
      2. 校验密码正确（密码是本人的第一证明；错误计入窗口失败）
      3. 校验邮箱验证码（verify_email_code_once，PURPOSE_UNFREEZE，60s 冷却/5 次作废——复用现有验证码机制）
      4. 全部通过 → 解冻 + 清空失败记录（含所在 IP 计数）→ 返回新 JWT（视为已登录）
```

- 失败处理：密码错或验证码错 → 401/409 且**计入窗口失败**；成功解冻即清零。
- 邮箱未绑定的老账号 → 自助解冻不可用，提示联系管理员（CLI/后台兜底解冻）。

### 3.2 为什么安全（关键论证）

- **正确的邮箱验证码 = 邮箱持有证明**。邮箱本身在注册时做了验证码绑定、且全局唯一——攻击者若偷得到目标邮箱，账号被不冻结也没意义；偷不到邮箱，就永远无法自助解冻。
- **密码仍然要验证**：攻击者猜密码的尝试被冻结挡住；真正的账号主人才知道密码，因此"正确密码 + 邮箱码"双重证明足以证明本人。
- **解冻接口本身有冷却**：验证码 60s 冷却 + 邮箱验证码 5 次作废，攻击者无法借解冻接口刷验证码。
- **每次解冻尝试失败也计入窗口失败**：攻击者无法用解冻接口绕过登录限流（两条路都通向冻结与冷却）。

### 3.3 恶意冻结攻击者的视角（v2 收益）

攻击者花 6 次失败把目标账号冻结 → 受害者 1 分钟内用自己邮箱+密码自助解冻 → 攻击者浪费 6 次尝试、暴露自己的 IP 计数（被计入每 IP 上限）→ 无 DoS 收益。攻击者改用分布式 IP 继续冻结 → 触发 §3.4 检测。

### 3.4 多 IP 分布式冻结检测（选配增强）

- **指纹判定**：同一账号冻结前，若失败记录中来源 IP 的去重数 ≥3（可配）→ 判定"疑似分布式攻击" → 冻结同时**临时提升阈值**：例如该账号需 12 次才冻结、且触发后进入 24 小时更严格冷却（而不是 5 分钟）。正常用户单 IP 输错不触发。
- **可选管理员通知**：触发分布式判定时向 `ADMIN_EMAILS` 发一封提示邮件（审计）。
- 默认配置见 §7。此增强为选配，默认关闭（开启需在失败记录落 IP hash——见 §3 数据模型，已含）。

## 4. 数据模型与存储

```
data/
├── login_failures/                    # 新增：按账号失败记录（文件名为 sha256(username_lower)，与邀请码同风格）
│   └── <sha256>.json
└── rate_limits/                       # 新增：每 IP 失败计数
    └── login_<ip_hash>.json
```

### 4.1 账号失败记录（含 IP 指纹，供 §3.4 选配）

```jsonc
{
  "username": "alice",                 // 冗余可读，便于审计
  "consecutive_failures": 3,           // 连续失败（驱动 L1）
  "last_failure_at": 1735000000.0,
  "failures": [                        // 10 分钟窗口内失败时间戳 + 来源 IP hash（供分布式判定）
    { "ts": 1735000000.0, "ip_hash": "sha256(ip)" }, …
  ],
  "frozen": false,
  "frozen_at": null
}
```

> 窗口条目数有上限（默认 20），量小无性能问题；`username` 明文仅存于文件内容（文件名哈希化），CLI 审计仍可直接读。

### 4.2 每 IP 计数（同邀请码机制风格，落盘跨 gunicorn worker 有效）

```jsonc
{ "window_start": 1735000000.0, "count": 7, "last_failure_at": 1735000100.0 }
```

## 5. 接口改动

### 5.1 登录接口（改 `POST /api/v1/auth/login`）

```
1. 每 IP 失败计数检查（≥10/10min → 429）
2. 读账号失败记录：
   ├─ frozen → 423（文案见 §2.1）
   ├─ L1 冷却 → 429 + Retry-After
   └─ 否则正常
3. 校验密码
   ├─ 正确 → 清空失败记录 → JWT（现状）
   └─ 错误 → 落账（连续+1、窗口追加、IP 指纹）
             ├─ 窗口≥6 → 冻结 → 423
             └─ 否则 401 统一文案
```

| 码 | 文案 |
|---|---|
| 401 | 用户名或密码错误。 |
| 429 | 尝试过于频繁，请在 X 分钟后重试。（`Retry-After`） |
| 423 | 该账号已临时冻结。若你是账号本人，请用正确密码 + 邮箱验证码自助解冻；否则请联系管理员 luchenstudio@163.com。 |

### 5.2 自助解冻（`POST /api/v1/auth/unfreeze`，公开；配套发码 `POST /api/v1/auth/unfreeze/send-code`）

- 发码 `{username, email}`：账号须存在（404）且冻结中（409）且 email 与绑定邮箱一致（422，未绑定提示联系管理员）→ 生成并发送解冻验证码（60s 冷却）。
- 解冻 `{username, password, email, code}`；校验顺序见 §3.1（先冻结检查 → IP 只读限流 → 密码校验 → 邮箱/验证码校验）。
- 目的：被冻结的本人用户 1 分钟自助恢复，管理员零介入。
- 复用邮箱验证码机制：新增用途常量 `PURPOSE_UNFREEZE = "unfreeze"`（60s 冷却、30 分钟有效、一次性、5 次作废——全部沿用现有实现）。
- 失败尝试同样计入登录窗口失败（防绕过）；解冻成功后清除账号与所在 IP 的失败计数。

### 5.3 管理员接口（`/api/v1/admin/`，白名单鉴权）

| 接口 | 说明 |
|---|---|
| `GET /api/v1/admin/users/frozen` | 冻结账号列表（用户名/冻结时间/失败数） |
| `POST /api/v1/admin/users/<username>/unfreeze` | 兜底解冻（邮箱未绑定老账号 / 极端情况） |

### 5.4 CLI（兜底）

```
python auth_admin_cli.py frozen list
python auth_admin_cli.py unfreeze <username>
```

## 10. 兼容性与影响面

- 只改 `login` 路由、新增 `unfreeze`/admin/CLI；注册、找回密码、JWT、老用户、数据目录不动。
- 正常用户无感（正确密码或偶尔输错 ≤3 次）；偶发误冻结可由本人邮箱自助恢复，不再依赖管理员。
- 与邀请码机制正交：邀请码管"谁能注册"，本补丁管"谁在登录"。
- 现有测试：smoke_test_auth.py 的错误密码用例（1 次失败，阈值内）不受影响；test_e2e.py 若有多次输错需核对（实施时全量跑测试确认）。

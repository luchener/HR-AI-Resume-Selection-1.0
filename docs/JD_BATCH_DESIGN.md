# 一份 JD × 批量简历（打分对比）设计

> 产品逻辑一句话：**同一个岗位 JD，对一批简历打同一把尺子，横向对比。**
> 现状偏差：API 允许一次传多份 JD，且 JD 被挂在某一份简历上（`job.resume_id`），
> 于是"3 份简历 + 2 份 JD"这种不成立的组合可以存在。本设计把 JD 拉成独立资源、
> 保证唯一，并把"多份 JD"从接口层直接排除。

---

## 1. 目标模型

```
             ┌──────────────┐
             │  岗位 JD × 1  │   ← 唯一、可复用、不归属任何简历
             └──────┬───────┘
                    │  同一把尺子
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
  简历 A         简历 B          简历 C        ← 批量上传，数量不限（受上限约束）
     │              │              │
     └──── 各生成 1 条 archive（resume_id, job_id）────┘
                    │
             按 job_id 分组 = 对比表
```

- 一次分析 = **1 份 JD + N 份简历** → N 条打分结果。
- 两个岗位要比？**分两次分析**，各自归档；不做"多 JD 同时分析"。
- 同一个任务再来一批候选人？**复用同一个 job_id**（内容相同即同一岗位），历史结果天然可比。

## 2. 数据模型

### 2.1 `data/jobs/<job_id>.json`

| 字段 | 现状 | 改为 |
|---|---|---|
| `job_id` | uuid4 | 不变 |
| `content` | JD 原文 | 不变（保留原文，不存归一化文本） |
| `processed` | 本地结构化 | 不变 |
| `user_id` | 有 | 不变（唯一性作用域） |
| `resume_id` | **必填，绑在某份简历上** | 降级为 `source_resume_id`：可空，**仅作溯源**，不参与校验/鉴权/唯一性 |
| `content_hash` | 无 | **新增**：归一化文本的 sha256，唯一性判据 |
| `created_at` / `updated_at` | 无 | 新增，审计与排序用 |

**唯一性约束**：`(user_id, content_hash)` 唯一。

> 为什么不按 `(resume_id, content_hash)`：JD 不属于简历。按简历去重，用户换一份简历再贴同一个岗位，
> 就会生成第二个 job_id，同一岗位的历史打分被切成两截，对比逻辑直接废掉。

### 2.2 内容归一化（落 hash 前的处理）

```
1. 去首尾空白（含 \u3000 全角空格）
2. 所有连续空白（空格 / \t / \r / \n）压缩为单个普通空格
3. 统一大小写？—— 不做。中文 JD 大小写无意义，且技术栈写法（React/react）
   缩写了会更乱
```

只影响 hash，**存储永远是用户原文**。所以"多个空行"和"一个空行"视为同一份 JD，
而"改了一个字的 JD"是新 JD。

### 2.3 查重索引

不建新表：`data/jobs/_index.json`，结构 `{"<user_id>": {"<content_hash>": "<job_id>"}}`，
写入走已有的 `_write_json`（原子写 + 文件锁）。文件不大（每用户百级），读整份即可。
索引损坏/丢失时退化为全目录扫（几十毫秒量级，可接受）。

## 3. 接口设计

### 3.1 `POST /api/v1/jobs/upload` —— 提交**一份** JD

**请求（推荐版）**
```json
{ "job_description": "岗位职责……", "source_resume_id": "（可选，仅溯源）" }
```

**过渡兼容**（保留一个版本，前端同批改掉）
```json
{ "job_descriptions": ["岗位职责……"] }   // 必须恰好 1 条，>1 → 422
```

**响应**
```json
{
  "job_id": "…",
  "created": true,          // false = 命中已有同内容 JD，直接复用
  "content_hash": "…",
  "message": "岗位已创建。"
}
```

- `resume_id` 不再必填，也不再校验归属（它已经不参与任何逻辑）。
- 幂等：同内容重复提交 → `created: false` + 已有 job_id，**磁盘不新增文件**。
- 校验顺序：Content-Type → 非空 → 恰好 1 条 → 单条 ≤ 20000 字 → 用户 JD 总量上限 → 限流 → 建/复用。

### 3.2 `POST /api/v1/resumes/hr-analysis` —— N 份简历 × 1 份 JD

接口已经支持 `{"resume_ids": [...], "job_id": "…"}`，**不改形状**，补三件事：

1. **单批上限**：`resume_ids` 最多 20 份（建议值，可配 `MAX_BATCH_RESUMES`），超限 422 并提示拆分。
2. **整批预占**：先算这次要 N 次额度，**一次性原子预占 N**，不够就整批拒绝：
   ```
   422/429 "本次分析共 3 份简历，需要 3 次额度，今日剩余 1 次。"
   ```
   而不是现在的"逐份预占、跑一半没额度了"——对比场景里半批结果是残缺的，比失败更糟。
   中途单份失败仍整批回滚未完成的部分（已完成的不退：结果已经给用户了）。
3. **批次语义**：这一批的 N 条 archive 共用同一个 `job_id`，前端按 job_id 分组即为对比表。

### 3.3 列表与删除

- `GET /api/v1/jobs?job_id=` 已有，不动。
- 新增 `GET /api/v1/jobs`（带分页）→ 岗位库列表，用于"复用历史岗位"。
- `DELETE /api/v1/jobs/<id>` 已实现（级联归档入回收站）；删除时同步清理 `_index.json` 里的映射。

## 4. 错误口径（统一 422，中文，可展示）

| 触发 | 响应文案 |
|---|---|
| 数组 > 1 条 | 一次只能提交一份岗位 JD。我们的打分方式是"同一份 JD 对多份简历横向对比"，多个岗位请分多次分析。 |
| 空 / 全空白 | 岗位 JD 不能为空。 |
| 超长 | 岗位 JD 不能超过 20000 字（当前 23104 字）。 |
| 批量超限 | 一次最多分析 20 份简历，请分批进行。 |
| 额度不足 | 本次分析共 3 份简历，需要 3 次额度，今日剩余 1 次。 |
| 用户 JD 总量超限 | 岗位库已达 200 条上限，请先清理历史岗位。 |

## 6. 存量数据迁移（一次性，幂等）

`scripts/migrate_job_dedupe.py`：

1. 扫 `data/jobs/*.json`，按 `(user_id, 归一化hash)` 分组。
2. 每组保留一条为"主"：优先保留被最多 archive 引用的那条，并列时保留最早创建的。
3. 其余文件删除，并把引用它们的 archive 的 `job_id` 改指向主条（archive 里存的是 job_id，
   改一个字段即可；归档内容本来就来自同一份 JD，改指不丢信息）。
4. 顺手给所有 job 补 `content_hash`、`source_resume_id`、`created_at`。
5. 重建 `_index.json`，打印报告：扫描 N 条、归并 M 组、删除 K 个文件、重指 J 条 archive。
6. `--dry-run` 先看报告再落盘；重复执行结果一致。

因为 `job.resume_id` **只写不读**，删除重复 JD 文件不会影响任何现有功能路径。

| 项 | 值（待你拍） | 作用 |

> 出事查不出人。这条一起改。

## 8. 测试清单

1. 同一份 JD 连传两次 → 同一个 job_id、`created:false`、磁盘只有 1 个文件。
2. 只差空行/多余空格的"同一份" → 仍判同。
3. 改一个字的 JD → 新 job_id。
4. 数组 2 条 → 422，零文件落盘。
5. 空串 / 40000 字 → 422，文案正确。
6. 1 份 JD + 3 份简历 → 3 条 archive，全部同一 job_id，各扣 1 次额度。
7. 批量 3 份但只剩 2 次额度 → 整批拒绝，**零** LLM 调用，提示"需要 3 次，剩余 2 次"。
8. 跨用户：A 的 JD 内容与 B 相同 → 各自独立 job_id（唯一性按 user_id 作用域）。
9. 删除 JD → 引用它的 archive 入回收站、索引同步清理。
10. 迁移脚本 dry-run 与实跑结果一致，重指后的 archive 仍能打开报告。
